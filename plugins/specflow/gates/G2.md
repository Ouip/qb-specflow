# G2 spec review (before dispatch)

Generic items. Product items are in the gate-extension file named in `specflow.md`. The report has one row per item (Pass / Fail / N/A with a reason), including items the product's extension file marks not applicable.

| Item | Check | Passes when |
|---|---|---|
| G2-1 | Testable interface: pure logic hides no global state; nondeterministic inputs such as time and randomness are parameters | Every external function's inputs are parameters or listed dependencies |
| G2-2 | Done criteria are machine-checkable | Each is "a command + its return value" or something greppable; "works correctly" does not count |
| G2-3 | Tests are in the right layer (layers are defined under "Test layers and commands" in `specflow.md`) | Each test row's layer follows the product's rule; cross-component tests are not in the unit layer |
| G2-4 | Verbatim match with upstream and downstream contracts | Types, field names and constants match the dependency contracts character for character |
| G2-5 | Every rule has a source | The Source cell is not empty; rules the spec invented are marked `(new)` and listed for the user to decide |
| G2-6 | Claims about drivers, libraries and hardware cite a source | Source `file:line` or a datasheet page; anything not found is marked "pending hardware" and listed in manual acceptance |
| G2-7 | Boundaries and combinations | Number, string and length rules state max, min, negative and empty; state machines list "B happens while A is in progress" |
| G2-8 | The spec is consistent with itself | Rule against rule, worked examples against rules, contract comments against section 4, compared item by item, with no contradiction |
| G2-9 | Variant binding | A value that holds for one hardware variant names that variant; an undecided variant fails the build, with no default |
| G2-10 | Every rule is verified | `<python> ${CLAUDE_PLUGIN_ROOT}/scripts/coverage.py <spec> --catalog <scenario catalogs…>` returns 0; the report pastes the output. This shows every Verify reference resolves, not that a test exercises the rule; behavior is checked at G5 |
| G2-11 | Couplings | For every couplings row involving this spec, the opposite side was reread and compared (the report says "coupling #n checked"); `<python> ${CLAUDE_PLUGIN_ROOT}/scripts/couplings.py <couplings table> --specs <spec folder> [--code <code repo>…]` returns 0 (with the product's value file, add `--values <file>` and `--cpp <preprocessor>` when a side uses strategy cpp; a FAIL, UNVERIFIED or BLOCKED value fails, a MANUAL row is compared by hand and named in the report); a quantity this spec shares with another component without a row gets a new row |

Specs designed in the same batch are reviewed together, so their types can be compared verbatim. On a fail, change the spec (ask the user first when a decision is involved); do not dispatch.
