# G5 code review (a separate sub-agent; never whoever wrote the code)

Runs once per dispatch; fixes for its findings are checked by G4 and the main session's fix check (`/specflow:dispatch` stage 3), not a second G5. Generic items. Product items are in the gate-extension file named in `specflow.md`. Scope = the prep commit to HEAD. Basis = this dispatch's spec, contracts, implementer rules and deferred list, **plus rules in other specs that name this component** (found with the impact search in `specflow.md`).

| Item | Check | Passes when |
|---|---|---|
| G5-1 | Tests test the behavior | No empty assertions, commented-out cases, or thresholds loosened to go green. With a verify map, `behavior.py --mutate` output is pasted; a rule whose `require` is not met is a Fail |
| G5-2 | The test list is complete | Every row of spec 5.1 has a matching test. A row whose premise is "the same object, continuing from the previous row" must not reinitialize that object anywhere on the test's path (helpers included); break the implementing line and the test must go red (`behavior.py --mutate` can show it) |
| G5-3 | Prohibitions not bypassed | The diff does not touch build settings, frozen contracts or other components |
| G5-4 | Architecture boundaries hold | The pure-logic layer has no framework or hardware headers; the adapter layer makes no business decisions |
| G5-5 | Error paths handled | More than the happy path works |
| G5-6 | Style, rule by rule | One row per implementer-rules style rule tagged [G5] (Conforms / Violates / N/A); read every touched file in full, not just the added lines |
| G5-7 | Reasons for letting something pass cite a source | A pass justified by "another component handles it" or "another layer has a timeout" cites that component's spec or code `file:line`; with none found, it cannot pass on that ground |
| G5-8 | No false claims | "Verified on device" backed only by host-side test evidence is sent back |
| G5-9 | Deferrals recorded | Every finding judged as not fixing, fix next time, worked around, or unchanged by agreement goes on the deferred list; items on the list marked "review at next G5" are reviewed this time |
| G5-10 | Check table | One row per in-scope rule; row count = number of in-scope rules; passes only with no Violates |
| G5-11 | Behavior the spec does not state | Each behavior in the diff that no spec rule states (an extra rejection, saturation, an extra cleared field, extra error handling) gets one finding of category "spec backfill", even when judged reasonable; dispatch close-out takes each one through `/specflow:change` or onto the deferred list |
| G5-12 | Five-axis quality review | Correctness, readability/simplicity, architecture, security and performance each have a conclusion and source locations or finding IDs (N/A has a reason). Confirmed correctness, safety or security defects are resolved; unresolved blocking risks return to the main session. Optional improvements and personal preferences are Advisory, not failures; existing rule and contract violations still block regardless of severity |
| G5-13 | Simplification assessed safely | The report gives proposals with a concrete benefit and preservation/verification plan, or "no useful simplification" with a reason. Proposals remain read-only and optional unless tied to an actual defect/rule violation. Any simplification already applied preserves required behavior, ordering, errors, compatibility, concurrency, timing and resource ownership with appropriate evidence; uncertain applied changes cannot pass on host tests alone. An implementer edit requires fresh G4 and the fix check |
| G5-14 | Problems in the spec itself | Each rule that contradicts another rule, is ambiguous, or cannot be implemented as written gets one finding of category "spec doubt", handed back to the main session for `/specflow:change`; it does not by itself send the code back. None found is a valid result |

## Check-table format (separate from the G5-6 style table)

| Rule ID | Code location `file:line` | Verification | Verdict | Notes |
|---|---|---|---|---|

- Rule ID: `<spec ID> <section>#<n>`.
- Verification: the test named in the Verify cell exists and fails when the rule is broken; for `untested: <reason>`, say whether the reason still holds. Write how far that was shown, as `behavior.py` names it: `MUTATION_VERIFIED` (fails with the rule broken), `TEST_PASSED` (ran and passed only), `REFERENCE_ONLY` (the test exists, nothing ran), `MANUAL_VERIFIED`, `WAIVED`, `UNVERIFIED`, `BLOCKED`. "The test exists" alone is `REFERENCE_ONLY`. For a rule tied to a couplings row, write that row's "How kept consistent".
- Verdict: Conforms / Violates / N/A / Cannot judge from diff. "Cannot judge from diff" goes back to the main session to check itself.
